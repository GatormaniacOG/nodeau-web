About

You own the GPUs. Nodeau makes them usable AI infrastructure.

A short explanation of what sits between a graphics card and a working AI endpoint, why a second machine changes the question, and which parts Nodeau takes on.

A GPU is not infrastructure

A modern graphics card is an enormous amount of compute sitting in a desktop case. Using it to run an AI model is a different problem from owning it. Between the two sit drivers, runtime libraries, model file formats, quantisation, container plumbing, a model server, an API, authentication, and something to keep it all running.

None of that is why anyone wanted to run a model. It is the tax.

Models are not interchangeable

Two models with the same name can need very different amounts of memory depending on how they were compressed, how much context you give them, and how many requests you want to handle at once. The honest way to know what a configuration costs is to measure it.

So Nodeau prefers a measurement, and when it does not have one it says so. On hardware it has measured, it uses the measurement. On hardware it has not, it derives a deliberately pessimistic figure from the model’s own architecture, keeps an extra margin back, and marks the decision as estimated.

That second path matters more than it sounds. The alternative — refusing everything unmeasured — is not caution, it is a platform that works on one graphics card. The honest position is not “we never estimate”; it is you can always see which one you got.

The number on the box is not the number you get

A card advertised with 10 GB does not hand 10 GB to a workload. Some of it cannot be addressed by the compute API at all. Your desktop is already using some — every window, every browser tab with a video in it. And a model that fits exactly with nothing to spare will fail the moment anything else asks for memory.

On the machine Nodeau was built on, the difference between the nameplate figure and what a workload can actually plan against is several hundred megabytes before the desktop is even considered. That gap is the difference between a model that runs and one that dies part-way through loading.

So Nodeau understands both sides

It observes the machine: which GPU, what the compute API can actually address, what is already in use, what Nodeau itself has committed elsewhere. It knows the model: measured peak memory for a specific configuration, plus a margin.

Then it decides. If the workload fits, Nodeau prepares everything it needs and starts it. If it does not, Nodeau refuses before scheduling it and shows the arithmetic — which is far more useful than a crash several seconds into loading.

That is the whole idea, and it is the part that makes this more than a wrapper around existing tools: decisions are made before scheduling, and every decision can be explained.

One GPU needs admission. Several need placement.

For an individual, all of that turns one PC into a private AI endpoint: a local, OpenAI-compatible API on a machine you already own, reachable only from that machine by default. The only question is does this fit here.

Add a second machine and a new question appears — which of these should run it, and why not the other one — and the tempting shortcut is to answer it with a count. Most infrastructure knows that a machine has a GPU. That is enough to place a workload and not nearly enough to know it will survive.

“GPU: 1” is not enough information. Two machines can both report one GPU and be nothing alike: different addressable memory, different amounts already spoken for by a desktop, a different copy of the model on disk that may or may not be the file it claims to be. Treating them as interchangeable is how a workload lands somewhere it cannot run.

So Nodeau does not add a second, looser rule for choosing a machine. It runs the same fit calculation once per candidate, keeps the reason each one won or lost, and prefers the tightest safe fit so a large card is not consumed by work a small one could hold. A workload that is already running and healthy stays where it is — a better score somewhere else is not a reason to restart something that is working.

That runs today across two machines with different NVIDIA generations. It is not yet in the public installer — see the roadmap, which labels every capability by what state it is actually in.

Why owned hardware

Running on hardware you control gives you locality, predictable capacity, and use of machines that already exist and are frequently idle. Data stays on the machine unless something you connect chooses to send it elsewhere.

It is not automatically cheaper. A GPU that runs a few hours a week is usually more expensive than paying per request, and anyone telling you otherwise is selling something. The case for owned hardware is control and predictability — and, often, that you already bought the card for something else.

Where it is today

What you can install is a Self-Hosted Alpha: one Linux machine, one NVIDIA GPU, one runtime, a small set of models. It has been installed from the published release onto a second machine with a different card, and it served a model there.

What runs but is not yet packaged is the multi-node control plane above — validated on those two machines together, with each observing its own hardware and verifying its own copy of the model. The site marks that In Alpha everywhere rather than folding it into what ships, because the difference is the whole difference between a claim and a download.

It is not production infrastructure. It has no uptime guarantee, it does not fail over to another machine, and it is not hardened for hostile multi-tenancy. Two machines is also not a fleet — it is two machines, and they belong to the same person.
